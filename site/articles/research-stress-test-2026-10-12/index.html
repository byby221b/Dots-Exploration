长上下文投机解码，怎样判断草稿缓存该压到多小

阅读约10分钟 · 公开研究主张审查

本期要检验的主张

一台机器同时处理多条长文本生成请求。目标模型负责最终答案，草稿器先猜几步，再交给目标模型一次核对。草稿器少看一些历史缓存，能否降低自己的开销，同时保留足够多可接受的猜测，让整批生成更快？

这是 MagicDec（ICLR 2025）明确研究的问题。把它收窄成可检验假设：在指定模型、硬件和长上下文负载下，保留目标模型的完整缓存，只压缩草稿器的缓存，经验证后输出不变，并使平均解码耗时下降、固定批量的吞吐上升。这里是建议审查的公开研究主张。

本期新增的是草稿缓存预算、有效推进长度与实测时延之间的取舍。这里沿一条链式草稿，给出可直接排除错误解释的实验。

先看一轮怎样工作

KV 缓存保存历史 token 的键和值，后续注意力计算会读取它们。长文本里，读这些历史数据本身可能很贵。MagicDec 的一种做法是让同一目标模型以较小的 KV 子集充当草稿器，最终验证仍读取完整 KV。节省发生在草稿阶段；没有把正式答案的历史直接删掉。

先限定为贪心解码：每次选目标分布中概率最高的 token；固定并列处理规则。假设已有前缀，草稿器连续给出 A、B、C。目标模型在一次带因果掩码的前向中检查这条链：

检查位置读取的前缀目标选择
第1步原前缀A：保留
第2步原前缀＋AB：保留
第3步原前缀＋A＋BD：替换 C

这一轮正式追加 A、B、D。C 后面的草稿即使已经算过，也不能接着使用，因为它们依赖了错误前缀。若三步都通过，原算法还能利用同次验证得到的下一位置分布，再追加一个 token。于是一次目标前向可以推进多步，而不只一步。

验证多个位置时可以复用读入的历史 KV；当 KV 搬运占主要成本，增加一些验证计算可能比逐 token 重复读取更便宜。这也解释了预算的作用：草稿 KV 过小，猜错得早，一轮推进很短；保留得更多，可能猜得更准，但草稿更慢。目标前向还要核对多个位置，验证也不是免费。

算法依据：ICML 2023，算法1。随机采样时，不能把“匹配最高概率词”当作同一规则，必须使用相应的接受概率与拒绝后的修正采样。理论保证是目标输出分布保持不变，不是同一个随机种子必然生成同一串文字。

先算对账，再谈接受率

用三个实测时间拆开每轮成本：D 是整段草稿的耗时，V 是完整目标模型的验证耗时，H 是采样、缓存整理和同步等额外耗时。都用毫秒；不要把每个 token 的草稿耗时误当成整段的 D。

我们要问的是：花掉这些时间，最终写入了多少个有效 token？对固定、同长度批量的稳定解码区间，可以直接记账：

每条序列的平均每 token 解码耗时
＝所有轮次的（D＋V＋H）之和
÷每条序列实际新增的 token 数。

这里先限定各序列推进一致的简单计时情形，便于理解；实际实现若各序列接受长度不同，应逐序列统计完成时间，并另外用整批实际输出 token 总数÷整批墙钟时间计算吞吐，不能拿一个平均接受率代替调度过程。

这个账本不要求每一步接受事件独立。它也避免把“每轮耗时÷每轮推进数”简单平均：推进1个和推进4个的两轮，不能赋予相同的 token 权重。靠近结束时，超过输出上限的额外猜测也不算有效产出。

决策量是整段解码耗时和有效吞吐；接受率只是解释它们的中间量。接受率升高，若 D 或 V 上升得更快，仍不值得增加缓存。固定批量、相同输出长度时，吞吐上升和整批时间下降本就是同一个计时结果的两种表达，不是两份独立证据。

原文支持到哪里，什么证据最值得警惕

直接支持：MagicDec §5.1 在 LLaMA-3.1-8B、PG-19、8张 A100 上比较完整自回归解码与 StreamingLLM 式稀疏 KV 草稿的自投机；每次用贪心解码生成96个 token，评估20个批次。它报告中长上下文下的收益，图6扫描缓存预算和批量，各点使用选出的最优猜测长度。表2中的最高2.51倍对应另一项具体配置：8张 H100、100000 token 前缀、批量41、猜测长度11、CWE任务、SnapKV草稿，并非所有请求的平均加速。

对泛化最强的反向证据也在同一篇里：短上下文、大批量时可能变慢；中等长度、批量尚不很大时，带 KV 压缩的小草稿模型可能优于自投机。静态选 KV 与逐步搜索 KV 也有不同的选择成本，不能只按接受率排优劣。上述结果限制的是适用区间，并未否定论文在特定长上下文设置下的收益。

还有一个影响判断的比较条件：图1(c)比较模型压缩与 KV 压缩时，两边使用的上下文长度不同。它能提出线索，却不能单独证明“相同上下文、相同总资源下，压 KV 总比缩模型好”。若要据此选择草稿器，下一步应做匹配条件的对照。

vLLM 的动态投机文档也把并发数和验证长度作为调节条件：更多并发请求同时验证更多 token，会增加计算需求。这是工程条件参考，不是对 MagicDec 的独立复现实验。原论文主要考察解码和同质批量；真实到达流里的排队、混合长度、首 token 等待时间，仍需另验。

最接近的方法，应该怎样比较

先比较同一目标模型的完整自回归解码，和“稀疏 KV 草稿＋完整验证”。这是同一输出要求下的直接对照。再加入普通小模型草稿，才检验收益究竟来自 KV 预算还是草稿器选择；这一步只在前一关通过后做。

StreamingLLM 式保留与 SnapKV 式选择，是可替换的草稿缓存策略，应分别给相同调参机会。连续批处理、注意力内核优化可以与投机组合，不能拿一个没有这些优化的基线来宣称投机胜出。直接压缩目标模型自己的 KV 会改变验证参照；如果加入它，应明确列为允许质量变化的另一目标，不混进“输出不变”的胜负表。

对推荐研究的可借鉴点，是把近似计算放在可由完整模型校验的阶段，并同时计入提案与校验成本。普通一次前向的 CTR 打分没有逐 token 生成链，不能据这篇论文直接推断 CTR 延迟收益；生成式推荐也要先确认其候选约束和验证语义能对应。

最低成本的区分实验：先做一张小网格

以下是未运行的建议方案，不需要先训练新草稿器，也不应一上来扫描所有模型。

第一关，正确性。固定目标权重、tokenizer、精度、解码规则和停止条件，先用贪心解码；保留完整目标 KV 与相同并列规则。检查不同拒绝位置、全部接受、提前结束和输出截断，逐 token 对照。发生差异时先定位数值或实现原因，不能把更短、不同的答案当成加速。随机采样是后续独立验收：检查接受/修正采样实现和分布一致性，单次文本相同不是证明。vLLM 官方说明也提醒浮点与批量变化会影响数值稳定性。

第二关，机制。选一个已具备可用推理实现的目标模型和一种公开文本任务。用开发样本预先选定两档前缀长度、两档可容纳的批量：让其中一档落在疑似 KV 读取瓶颈，另一档作为对照。固定一次猜测3个 token，只扫描两档草稿 KV 预算，例如256和512个历史位置；是否保留特殊起始位置必须随实现明确记录。这四个负载点、每点两个预算，加上关闭投机的基线，已能检验“省草稿成本是否被拒绝与验证开销抵消”。这些数值是初筛建议，不是最优参数结论。

每个格子记录 D、V、H、连续接受长度分布、实际有效 token 数、显存峰值和整批时间。区分缓存选择的一次性准备成本与逐轮成本；先报告纯解码，再把准备、prefill和结束处理加回完整请求，不能藏在计时区间外。

第三关，公平复核。只对通过初筛的格子加入小模型草稿、另一种 KV 选择，以及猜测长度1/3的消融。比较两种 KV 选择时，先固定相同草稿 KV 预算和猜测长度，隔离选择方法本身的影响；再在相同总资源和调参预算下比较各自最优配置。所有方案使用同一总 GPU 数和显存上限、相同目标精度、内核与预热条件；小草稿器所占资源也算入。开发集上给相同搜索预算，锁定配置后再测未参与选参的样本，不能各自挑最有利的请求。

最后回放相同到达流，分开报告首 token 延迟、每输出 token 时间、p50/p95 请求完成延迟，以及满足预定延迟要求的完成请求数/秒。按完整请求或批次做重复测量与区间估计，别把同一请求中的 token 当作独立样本。完成率、输出长度分布和拒绝/超时请求都要保留，避免“丢掉慢请求后更快”。

看到什么结果，才继续或修改判断

先写下业务可接受的尾延迟和最小有用收益，再看测试结果：

  • 正确性检查失败：暂停无损加速结论，先修复或缩小保证范围。
  • 缓存预算增大后接受长度增加，但完整耗时不降：否定“更高接受率就值得更多 KV”，保留较小预算或关闭投机。
  • 收益只出现在长文本、固定批量，混合到达流下消失：将结论限定在该负载，或改成按长度与并发启停；不能宣传为通用服务加速。
  • 匹配硬件、内核、调参预算后，稳定收益消失：放弃该部署配置的提速判断；这不等于整项方法被证伪。
  • 正确性通过，未参与选参的负载上完整耗时和服务指标均达预定门槛：才值得扩大覆盖，并继续检查更长尾、更高并发和缓存准备成本。

本期要带走的判断方式很具体：每多留一份草稿缓存，就看它多换回多少有效推进，以及为此多花了多少完整时间。不要只凭缓存压缩率、模型参数量或接受率选方案。
